Contributor @TusharPardhe responded with research suggestions including using log-space edge weights for multiplicative rate composition.

**In-Memory Node Store proposal**: @shortthefomo also proposed an RWDB In-Memory Node Store that eliminates disk I/O for the node store while retaining ledger state through shared_ptr chains — [Discussion #559](https://github.com/XRPLF/XRPL-Standards/discussions/559).

**xrpl-py currency decoding bugs**: Community member @RaymondSeven filed two issues in xrpl-py:
- [xrpl-py#1007](https://github.com/XRPLF/xrpl-py/issues/1007): `UnicodeDecodeError` when rendering valid 160-bit currency codes with non-ASCII bytes — rippled and xrpl.js render these safely as hex strings, but xrpl-py crashes.
- [xrpl-py#1006](https://github.com/XRPLF/xrpl-py/issues/1006): Malformed 160-bit currency codes with non-zero reserved bytes are incorrectly classified as ISO-style codes because only `buffer[0]` is checked.

**xrpl4j codec and parser issues**: @RaymondSeven also filed two issues in xrpl4j:
- [xrpl4j#805](https://github.com/XRPLF/xrpl4j/issues/805): `BinaryParser` decodes 2-byte variable-length fields with an incorrect formula, producing wrong lengths for the 193–12480 byte range.
- [xrpl4j#804](https://github.com/XRPLF/xrpl4j/issues/804): Binary codec lacks recursion depth limits for nested STObject/STArray parsing, which could exhaust the host stack on deeply nested payloads.

**Public server listings**: Two open PRs propose adding third-party hosted XRPL RPC providers to the public servers page — [xrpl-dev-portal#3674](https://github.com/XRPLF/xrpl-dev-portal/pull/3674) (GetBlock) and [xrpl-dev-portal#3408](https://github.com/XRPLF/xrpl-dev-portal/pull/3408) (dRPC NodeCloud).

## Plain English Summary

This week was all about documentation. The team behind xrpl.org merged 27 changes to the developer portal — the biggest batch being the rename of the core server software from "rippled" to "xrpld." If you've ever looked at XRPL documentation, you'll notice references to "rippled" everywhere — in page titles, configuration examples, command-line instructions, and diagrams. All of those are now being updated to "xrpld" for consistency with the upcoming version 3.2.0 release. Importantly, old links won't break; redirects are in place so existing bookmarks and references still work. The portal also gained a brand-new section on "agentic transactions" — a guide for developers building AI agents that can make payments on the XRP Ledger — and a fresh tutorial for sending Multi-Purpose Tokens in JavaScript, Python, and Go, replacing the older version.

On the tools side, the Java SDK (xrpl4j) fixed a subtle but real bug: if your application passed the most negative possible number to a function that converts XRP drops, it would silently produce the wrong result due to how Java handles number overflow. That's now caught and prevented. The API server Clio published a second release candidate (2.7.1-rc2) that fixes how it handles connections through network proxies — specifically, it now correctly identifies clients when a proxy reuses the same connection for different users. In the XRPL-Standards repo, the specification for the WASM virtual machine (XLS-0102) now documents explicit memory size limits, and a credential error code was corrected. Community members also filed several issues identifying inconsistencies in how the Python and Java SDKs decode certain currency codes and binary data, which will help improve cross-SDK compatibility.

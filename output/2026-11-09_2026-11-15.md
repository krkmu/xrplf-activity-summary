### Protocol & Feature Work (rippled — merged to develop)

- **Batch preflight allocation optimization**: [rippled#8627](https://github.com/XRPLF/rippled/pull/8627) (+29/−25) — Replaces heap-allocating `std::unordered_set`/`std::unordered_map` containers in `Batch::preflight` with `std::flat_set`s backed by inline `small_vector` storage. Since `preflight` runs for every submitted and relayed Batch (XLS-56) transaction, this eliminates per-insertion heap allocations from a hot path.

### Bug Fixes & Stability (rippled — merged to develop)

- **Reset ledger save state on database write failure**: [rippled#8662](https://github.com/XRPLF/rippled/pull/8662) (+141/−2) — When the relational database reports an error during `saveValidatedLedger()`, the pending-saves entry and `SAVED` flag are now cleared so the next save attempt proceeds as a first attempt rather than being skipped. Synchronous callers waiting on that ledger sequence also wake up correctly.

- **Complete every queued node store read on shutdown**: [rippled#8658](https://github.com/XRPLF/rippled/pull/8658) (+147/−6) — `Database::asyncFetch()` now completes reads immediately with no object when the queue is closed, and `Database::stop()` drains all queued reads after releasing the lock. This prevents shutdown hangs caused by callbacks that never fire.

- **Add type validation to `log_level` RPC parameters**: [rippled#7595](https://github.com/XRPLF/rippled/pull/7595) (+38/−0) — The `log_level` admin RPC called `asString()` on `severity` and `partition` without checking their JSON type. Non-string values (e.g. `{"severity": 5}`) could throw or return an internal error. Now returns `rpcINVALID_PARAMS` for invalid types. Contributed by community member @harshitgupta62.

### Refactoring & Architecture (rippled — merged to develop)

- **Avoid re-parsing `STTx` during transaction relay**: [rippled#8593](https://github.com/XRPLF/rippled/pull/8593) (+133/−5) — Adds an `Overlay::relay` overload that accepts the already-parsed `STTx`. Both `NetworkOPs` and `OpenLedger` now use it, eliminating a redundant full parse (template application, `sha512Half`, batch build) on every relayed transaction.

- **Avoid copying `STTx` in NetworkOPs**: [rippled#8582](https://github.com/XRPLF/rippled/pull/8582) (+2/−2) — Two sites in `NetworkOPsImp` deep-copied an `STTx` via `auto const sttx = *transaction->getSTransaction()` when they only needed to read it. Changed to `auto const&` to bind to the shared pointer's target.

- **Stop sending `TMTransaction.receiveTimestamp` and deprecate it**: [rippled#8702](https://github.com/XRPLF/rippled/pull/8702) (+2/−9) — The `receiveTimestamp` field was added in 2011 so relaying nodes could annotate transactions with their clock. Every sender has set it from its own clock since 2012, and no receiver reads it. The field is now deprecated in the protobuf definition, and no code populates it.

- **Remove ten unused peer protocol message fields**: [rippled#8701](https://github.com/XRPLF/rippled/pull/8701) (+13/−27) — Removes fields from five peer protocol messages that no code writes or reads, and reserves their field numbers. Also removes the one piece of code that touched any of them.

- **Remove two unused headers**: [rippled#8704](https://github.com/XRPLF/rippled/pull/8704) (+0/−277) — Removes `results.h` and `Output.h`, following up on the dead-code wave from the previous week.

- **Remove unreachable publish loop**: [rippled#8485](https://github.com/XRPLF/rippled/pull/8485) (+17/−37) — `pubProposedAccountTransaction` declared an `accountHistoryNotify` vector, never inserted into it, and then tested and iterated it. Removed.

- **`json::Value` accepts `std::string_view`**: [rippled#8486](https://github.com/XRPLF/rippled/pull/8486) (+175/−3) — Adds a constructor and `operator==` so callers holding a `string_view` no longer need to materialize a `std::string` just to construct or compare a JSON value.

## Plain English Summary

This week's work on the XRP Ledger focused on making the core server faster and cleaner, while the client libraries and documentation continued to mature. In the server software (rippled), developers eliminated unnecessary work during transaction processing — when a node relays a transaction to its peers, it was previously parsing the transaction data from scratch even though it had already parsed it moments earlier. Two changes fixed this by passing along the already-parsed transaction instead. Another optimization removed heap memory allocations from a frequently-run validation check for Batch transactions, replacing them with pre-sized inline storage. A separate fix addressed a scenario where, if the database failed while saving a validated ledger, the server would incorrectly skip retrying that save — now the save state is properly reset so recovery can proceed.

For the JavaScript library (xrpl.js), the team made an important decision about release strategy. A recent change that would have altered how XRP amounts are returned (using a high-precision number type instead of a regular JavaScript number) was moved off the main development branch onto a separate branch for version 6.0.0. This means the next release from the main branch can ship as a non-breaking 5.4.0 update, giving developers time to prepare for the bigger change. The Java library (xrpl4j) made a breaking improvement to how its JSON configuration works — previously, its settings could accidentally affect other parts of a Java application that share the same JSON processing machinery, and now those settings only apply to XRPL-specific types. On the documentation side, the developer portal published an important announcement: both the Testnet and Devnet test networks will be **reset on November 25**, deleting all accounts, balances, and other data. Developers who rely on these networks should plan to re-create their test data from the faucet afterward.

For the latest updates, follow [@XRPLF](https://x.com/XRPLF) and [@RippleXDev](https://x.com/RippleXDev) on X, and see the [Testnet/Devnet reset announcement](https://xrpl.org/blog/2026/testnet-devnet-reset) for details on the upcoming reset.

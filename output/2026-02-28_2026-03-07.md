# XRPL Developments Weekly Summary: 2026-02-28 to 2026-03-07

## Headline

The `server_definitions` RPC endpoint gained a major upgrade this week: transaction formats and flags are now included in its response, closing a long-standing gap that client library authors have worked around for years. Alongside that, a critical xrpl-py bug was fixed where incorrect SField definitions were silently corrupting Lending Protocol and DynamicMPT transactions during serialization.

## What Shipped

### Protocol & API

**`server_definitions` now includes transaction formats and flags** — [rippled#6321](https://github.com/XRPLF/rippled/pull/6321) (+1169/-503 in 29 files) closes [#5151](https://github.com/XRPLF/rippled/issues/5151), a request open since at least 2024. The `server_definitions` RPC response now exposes transaction and ledger entry formats and flags, enabling client libraries to introspect the protocol's full structure at runtime rather than hardcoding it. This is the foundation for the XLS-97 (Formats, Fields and Flags) spec. The old `DeliverMax`-in-definitions issue was also resolved as part of this work.

**`gateway_balances` RPC fix for MPT** — [rippled#6143](https://github.com/XRPLF/rippled/pull/6143) (+44/-1, labeled **API Change**) fixes a case where the `gateway_balances` RPC — which is IOU-specific — would fail when it encountered Multi-Purpose Token entries. **Assorted WASM/smart-escrow fixes** — [rippled#6376](https://github.com/XRPLF/rippled/pull/6376) improves comments, removes the possibility of negative gas limits, and improves memory bounds error handling in the smart escrow / WASM execution path.

### Confidential MPT (XLS-96)

Multiple fixes landed this week as part of an ongoing audit series:

- **Shared `r` for equality proof** — [rippled#6496](https://github.com/XRPLF/rippled/pull/6496): Adopts a shared `r` value for the ConfidentialMPTSend equality proof, making the proof smaller and lighter.
- **Vault invariant rounding** — [rippled#6217](https://github.com/XRPLF/rippled/pull/6217): Relaxes Vault Deposit/Withdraw/Clawback invariants for IOUs to allow a minimal rounding tolerance (1×10⁻¹³), while keeping XRP and MPT tolerances at zero. (Note: this PR had an outstanding change request that was subsequently addressed before merge.)
- **Replay tests** — [rippled#6451](https://github.com/XRPLF/rippled/pull/6451): Adds 306 lines of replay tests for Confidential MPT transactions.

**xrpl-py: Critical serialization bug fixed** — [xrpl-py#918](https://github.com/XRPLF/xrpl-py/pull/918) fixes incorrect SField definitions in the binary codec's `definitions.json`. Specifically: `sfMutableFlags` (DynamicMPT) was defined with field code nth=54 instead of the correct nth=53, causing xrpl-py to serialize `MutableFlags` with the field code that rippled assigns to `sfStartDate`, corrupting transactions on the write path. Additional entries for `PreviousPaymentDueDate` and `LoanScale` were also corrected. Validators and operators using xrpl-py to construct DynamicMPT or Lending Protocol transactions should update immediately.

## Plain English Summary

The biggest news for developers this week is a long-overdue improvement to a rippled API endpoint called `server_definitions`. Until now, this endpoint returned information about XRPL data fields but left out transaction types and their associated flags — meaning client libraries (apps that talk to the network) had to hardcode that information themselves, or go without. The change merged this week adds that missing information directly to the response. This makes it easier to build tools that automatically understand new transaction types without manual updates.

A more urgent fix landed in the Python XRPL library (xrpl-py): a bug was discovered where certain transaction fields for the Lending Protocol and DynamicMPT features were assigned the wrong internal numbers in the library's data dictionary. In practice, this meant that when a developer used xrpl-py to build a DynamicMPT transaction, the library was quietly writing one field's value into a completely different field's slot before sending it to the network — corrupting the transaction without any visible error. Developers using xrpl-py to interact with these features should update to the latest version immediately. The fix is available at [xrpl-py#918](https://github.com/XRPLF/xrpl-py/pull/918).

Finally, Clio — the API server that many applications use to query historical XRPL data — had a startup crash fixed in this week's nightly build. A recent code change had introduced a bug where Clio would fail to start at all if it couldn't find a local cache file, which would have affected any operator spinning up a fresh Clio instance. That fix is included in the [nightly-20260306](https://github.com/XRPLF/clio/releases/tag/nightly-20260306) release. Separately, a potential stability issue was reported for nodes that have been "amendment-blocked" (running an older version that doesn't support newer features): such nodes may crash when the network forces a ledger jump involving transaction types they don't recognize. This has been observed on a related network but not yet confirmed on the main rippled codebase — validators running older software should follow [rippled#6492](https://github.com/XRPLF/rippled/issues/6492) for updates. Follow @XRPLF and @RippleXDev on X for ongoing developments.

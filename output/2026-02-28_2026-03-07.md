## What Shipped

### Protocol & API

**`server_definitions` now includes formats and flags** — [rippled#6321](https://github.com/XRPLF/rippled/pull/6321): The `server_definitions` RPC method now returns transaction formats, ledger entry formats, and flag values, closing [#5151](https://github.com/XRPLF/rippled/issues/5151) and [#5506](https://github.com/XRPLF/rippled/issues/5506). This has been a long-standing request from wallet developers, custody solutions, and SDK authors who needed a machine-readable source of truth for all transaction types and their flags. The change carries the **API Change** label (+1169/-503 across 29 files).

**`gateway_balances` fix for MPT** — [rippled#6143](https://github.com/XRPLF/rippled/pull/6143): The `gateway_balances` RPC now correctly skips MPToken entries, since gateway balances are an IOU-only concept. Previously, encountering an MPT type could produce incorrect results. Labeled **API Change**.

**Vault invariant rounding** — [rippled#6217](https://github.com/XRPLF/rippled/pull/6217): Vault deposit, withdraw, and clawback invariants now tolerate a minimal relative discrepancy for IOU balance comparisons (tolerance: 1×10⁻¹³; zero tolerance for MPT/XRP). This allows the `InvariantsV1_1` feature to handle rounding edge cases that arise from IOU arithmetic without false failures.

**Defensive sfData length check for WASM** — [rippled#6449](https://github.com/XRPLF/rippled/pull/6449): Added a bounds guard in `EscrowFinish::doApply()` ensuring WASM-produced `sfData` cannot exceed the protocol's maximum allowed length before being written to the ledger. Labeled as a bug fix.

## Plain English Summary

**A better schema endpoint for developers.** One of the most impactful changes this week is an upgrade to the `server_definitions` API — a special endpoint that XRPL nodes expose to tell software what kinds of transactions and ledger entries exist, and what flags they support. Previously, this endpoint was missing a lot of that information, forcing SDK authors and wallet builders to hard-code it themselves. Now, the endpoint returns a complete, machine-readable description of every transaction type, ledger entry type, and flag value the ledger understands. Practically, this means future client libraries can be built to support new XRPL features automatically, without requiring manual updates every time a new amendment is added.

**A silent data corruption bug fixed in xrpl-py.** A more urgent item this week is a bug fix in xrpl-py, the Python SDK for the XRP Ledger. Two fields in the binary encoding definitions were wrong: `MutableFlags` (used in DynamicMPT transactions) was assigned the wrong internal number, causing it to be encoded identically to an unrelated field called `StartDate`. This meant that Python applications building DynamicMPT or Lending Protocol transactions were silently producing malformed data. The fix corrects the field numbers and renames `PreviousPaymentDate` to its correct name `PreviousPaymentDueDate`. Anyone using xrpl-py to work with these newer features should update their library immediately.

**A potential stability issue for older nodes — worth watching.** A community contributor filed a bug report describing a scenario where XRPL nodes running older software — specifically those that are "amendment-blocked" (running code that doesn't support a newer amendment the network has adopted) — may crash in certain circumstances. The crash can happen when the node tries to read a transaction that contains field types it doesn't recognize. This has been confirmed on a related network (Xahau) but has not yet been tested or confirmed on rippled itself. The core team has acknowledged it. Validators running older node software should monitor [rippled#6492](https://github.com/XRPLF/rippled/issues/6492) for updates.

For ongoing updates, follow [@XRPLF](https://x.com/XRPLF) and [@RippleXDev](https://x.com/RippleXDev) on X.

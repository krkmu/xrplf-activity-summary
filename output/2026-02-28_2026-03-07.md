# XRPL Developments Weekly Summary: 2026-02-28 to 2026-03-07

## Headline

The `server_definitions` RPC endpoint now returns transaction and ledger entry formats and flags — closing a long-standing gap that forced client libraries to hardcode schema data. Simultaneously, xrpl-py received critical serialization fixes for Lending Protocol (XLS-66) and DynamicMPT (XLS-94) fields that were corrupting transactions on the write path.

## What Shipped

### Protocol & API

**`server_definitions` now includes formats and flags** — [rippled#6321](https://github.com/XRPLF/rippled/pull/6321) (labeled **API Change**, closes [#5151](https://github.com/XRPLF/rippled/issues/5151)) adds transaction formats, ledger entry formats, and flag definitions to the `server_definitions` response. This resolves a multi-year request: client libraries previously had to maintain their own copies of transaction fields and flag values. With this change, a single RPC call exposes the full schema needed for serialization, deserialization, and transaction construction. Related issue [#5506](https://github.com/XRPLF/rippled/issues/5506) (`DeliverMax` in `server_definitions`) was closed as resolved by this PR.

**Gateway balance API fixed for MPT** — [rippled#6143](https://github.com/XRPLF/rippled/pull/6143) (labeled **API Change**, approved) corrects the `gateway_balances` RPC to skip MPT-type entries, which are not applicable to that endpoint. Previously, the presence of MPT holdings could cause incorrect behavior on gateway balance queries.

**Defensive WASM data size check** — [rippled#6449](https://github.com/XRPLF/rippled/pull/6449) adds a bounds check in `EscrowFinish::doApply()` to ensure WASM-produced `sfData` does not exceed the protocol's maximum allowed length before writing it into an Escrow ledger entry.

**Vault invariant rounding for IOUs** — [rippled#6217](https://github.com/XRPLF/rippled/pull/6217) relaxes Vault Deposit, Withdraw, and Clawback invariants to allow a minimal discrepancy (tolerance of 1×10⁻¹³) for IOUs, while keeping zero tolerance for MPT and XRP. This accommodates rounding artifacts in IOU arithmetic without loosening correctness guarantees for other asset types.

**Confidential MPT proof optimization** — [rippled#6496](https://github.com/XRPLF/rippled/pull/6496) adopts a shared `r` value for the ConfidentialMPTSend equality proof, reducing proof size and computational overhead.

**Smart Escrow fixes** — [rippled#6376](https://github.com/XRPLF/rippled/pull/6376) applies several correctness fixes to the WASM/smart escrow subsystem: improved SField error handling, removal of the possibility of negative gas limits, and cleaner memory bounds error handling.

### xrpl-py: Critical Serialization Fix

[xrpl-py#918](https://github.com/XRPLF/xrpl-py/pull/918) corrects two incorrect SField definitions in the binary-codec `definitions.json`:
- `sfMutableFlags` (DynamicMPT) was mapped to field code `nth=54` instead of the correct `nth=53`, which caused xrpl-py to serialize `MutableFlags` with the field code rippled assigns to `sfStartDate`, corrupting transactions on the write path.
- `PreviousPaymentDate` was renamed to `PreviousPaymentDueDate` to match the upstream spec.

Developers using xrpl-py to construct DynamicMPT or Lending Protocol transactions should update immediately.

## Plain English Summary

**A long-awaited schema API improvement landed this week.** The XRPL node software now includes full transaction schemas — field definitions, ledger entry formats, and flag values — in a single RPC response called `server_definitions`. Previously, developers building wallets, exchanges, or tools had to maintain their own copies of this information and update them manually whenever the protocol changed. With this change, any client application can ask a running node for the complete rulebook and use it directly. This reduces the chance of client libraries drifting out of sync with the actual protocol.

**A serialization bug in the Python SDK was fixed.** The xrpl-py library had two incorrect field definitions in its internal codec data: one field used the wrong numeric code, meaning Python applications serializing certain Lending Protocol or DynamicMPT transactions would produce corrupted binary data that rippled would reject or misinterpret. This is now corrected. Developers using xrpl-py to work with these newer features should update their library as soon as the fixed version is available.

**Infrastructure cleanup continues at pace.** The rippled codebase is undergoing a coordinated reorganization — transaction handler files are being split into one-class-per-file, the build toolchain's CMake formatter was upgraded, and a growing set of static analysis checks are being turned on to catch categories of programming mistakes automatically. Clio, the API server layer, fixed a startup regression and has a new feature in review that will prevent multiple nodes in a cluster from simultaneously loading their data cache — reducing load spikes on startup. None of these changes affect how the network validates transactions, but they reduce the risk of bugs being introduced in future development.

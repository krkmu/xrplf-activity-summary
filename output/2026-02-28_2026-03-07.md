# XRPL Developments Weekly Summary: 2026-02-28 to 2026-03-07

This week's most significant merged work spans three areas: `server_definitions` now exposes transaction and ledger entry formats and flags (closing a long-standing feature request), Confidential MPT received a lighter-weight equality proof and additional test coverage, and the XRPL dev portal got a major tutorial information architecture overhaul landing nearly 24,000 file changes.

## What Shipped

### Protocol & API
**`server_definitions` now includes Formats and Flags** — [rippled#6321](https://github.com/XRPLF/rippled/pull/6321) (+1169/-503 in 29 files) closes [issue #5151](https://github.com/XRPLF/rippled/issues/5151) and [issue #5506](https://github.com/XRPLF/rippled/issues/5506), both of which date back years. The `server_definitions` API response now includes transaction and ledger entry formats, field flags, and related metadata that client libraries previously had to hard-code. Labeled **API Change**: any tooling that parses `server_definitions` output should validate its handling of the new fields.

**`gateway_balances` fixed for MPT** — [rippled#6143](https://github.com/XRPLF/rippled/pull/6143) (+44/-1, labeled **API Change**) corrects a case where the `gateway_balances` RPC, which only applies to IOUs, was not properly skipping MPT-type token entries. Approved by one reviewer.

**Vault invariant rounding for IOUs** — [rippled#6217](https://github.com/XRPLF/rippled/pull/6217) (+506/-74) relaxes Vault Deposit, Withdraw, and Clawback invariants for IOUs to allow a relative tolerance of 1×10⁻¹³ for floating-point discrepancies. XRP and MPT invariants remain zero-tolerance. Note: this was merged despite an outstanding CHANGES_REQUESTED from one reviewer, whose follow-up PR (#6246) addresses some of the requested changes separately.

**Assorted WASM/EscrowFinish fixes** — [rippled#6376](https://github.com/XRPLF/rippled/pull/6376) (+116/-60) improves comments, tightens SField error handling, removes the possibility of negative gas limits, and cleans up memory bounds error handling in the WASM/smart escrow path. [rippled#6449](https://github.com/XRPLF/rippled/pull/6449) (+5/-0) adds a defensive size check to ensure WASM-produced `sfData` cannot exceed the protocol maximum before being written into an Escrow ledger entry.

**xrpl-py binary codec corrections** — [xrpl-py#918](https://github.com/XRPLF/xrpl-py/pull/918) (+33/-16) fixes two incorrect SField definitions in the binary codec `definitions.json`: `sfMutableFlags` was assigned field code nth=54 instead of the correct nth=53, which caused xrpl-py to serialize `MutableFlags` using the field code for `sfStartDate`, corrupting transactions on the write path. `PreviousPaymentDate` was also renamed to `PreviousPaymentDueDate` to match the current spec.

## Plain English Summary

**What's new in the ledger protocol:** The `server_definitions` API call — which nodes expose so that wallets and client libraries can understand XRPL's data structures — now includes transaction formats, ledger entry type formats, and flag definitions. Previously, developers had to manually maintain copies of these definitions in their own code, which fell out of sync as the protocol evolved. Now, a client library can ask any node directly and get a complete, up-to-date picture. This is a meaningful improvement for anyone building tooling on top of XRPL. Additionally, the `gateway_balances` RPC was fixed to correctly skip MPT-type tokens, which it previously did not handle, and Vault (XLS-65) invariant checks were relaxed by a tiny margin for IOU rounding errors — this is an internal correctness fix that prevents the ledger from rejecting valid Vault transactions due to floating-point imprecision.

**Critical fix in the Python SDK:** The xrpl-py library had a bug where a field used in DynamicMPT (XLS-94) and Lending Protocol (XLS-66) transactions was being serialized with the wrong internal identifier. In practice, this meant any transaction using `MutableFlags` would be written to the ledger using the wrong field slot, corrupting the data. This has been corrected in [xrpl-py#918](https://github.com/XRPLF/xrpl-py/pull/918). If you are building applications involving DynamicMPTs or the Lending Protocol using Python, you should update to the latest xrpl-py.

**Something to watch if you run a node:** An issue filed this week ([rippled#6492](https://github.com/XRPLF/rippled/issues/6492)) describes a scenario where amendment-blocked nodes — nodes running older software that hasn't enabled the latest amendments — may crash when the network switches to a newer ledger version containing transaction fields the older node doesn't recognize. This was confirmed on a related network and the rippled code appears to share the same paths. No fix has landed yet, but it is triaged and being investigated. Node operators who intentionally keep nodes behind the amendment frontier should monitor this issue.

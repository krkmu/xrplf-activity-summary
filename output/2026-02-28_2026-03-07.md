## What Shipped

### Protocol & API

**`server_definitions` now exposes transaction formats, ledger entry formats, and flags** — [rippled#6321](https://github.com/XRPLF/rippled/pull/6321) (+1169/-503, 29 files) closes [#5151](https://github.com/XRPLF/rippled/issues/5151), a feature request that had been open since 2024. Client libraries and custody solutions can now programmatically discover transaction structure and flag values without hardcoding them. Labeled **API Change**.

**Gateway balance RPC fixed for MPT accounts** — [rippled#6143](https://github.com/XRPLF/rippled/pull/6143) correctly skips Multi-Purpose Token entries when computing gateway balances, since this RPC is IOU-only. Previously MPT holdings caused incorrect behavior. Labeled **API Change**, approved by a core team reviewer.

**xrpl-py: Critical binary codec fix for Lending Protocol and DynamicMPT** — [xrpl-py#918](https://github.com/XRPLF/xrpl-py/pull/918) corrects wrong field codes in `definitions.json`. `sfMutableFlags` was mapped to field code 54 instead of the correct 53 — meaning any Python-constructed transactions for DynamicMPT were serialized with the wrong field code, colliding with `sfStartDate` and silently corrupting the binary. This fix is important for any developer using xrpl-py with these features.

**Smart Escrow: defensive data length check** — [rippled#6449](https://github.com/XRPLF/rippled/pull/6449) adds a size guard on WASM-produced `sfData` in `EscrowFinish`, preventing oversized data from being written into ledger entries. A small but important safety fix flagged during AI-assisted code review.

**Vault invariants updated for IOU rounding** — [rippled#6217](https://github.com/XRPLF/rippled/pull/6217) relaxes Vault Deposit/Withdraw/Clawback invariants for IOUs to allow a minimal rounding tolerance (1×10⁻¹³). MPT and XRP tolerances remain zero. This was previously blocked by outstanding change requests; the invariant was rewritten to use relative distance checking.

**ConfidentialMPT (XLS-0096): lighter equality proofs and ongoing audit fixes** — [rippled#6496](https://github.com/XRPLF/rippled/pull/6496) adopts a shared `r` value in equality proofs, reducing proof size. Separate audit-item PRs were also merged this week addressing credential checks (#6471 is still open), destination version increment (#6462 open), and clawback version increment (#6454 open) — watch the In Progress section.

**XRPL-Standards: Confidential MPT spec updates** — Three spec PRs merged: [#491](https://github.com/XRPLF/XRPL-Standards/pull/491) (credential handling), [#487](https://github.com/XRPLF/XRPL-Standards/pull/487) (merge inbox with zero balance), and [#486](https://github.com/XRPLF/XRPL-Standards/pull/486) (invariant additions), keeping the spec in sync with audit-driven implementation fixes.

## Plain English Summary

**What changed with `server_definitions`?**
The XRPL node software can now answer a simple question that developers have been asking for two years: "What does a valid transaction look like?" Previously, client libraries had to hardcode transaction field names and flag values. Now, a single API call to `server_definitions` returns all that information directly from the node — including every transaction type, ledger object type, and their allowed flags. This means wallet software, custody systems, and developer tools can stay in sync with the ledger's rules automatically, even as new features are added.

**What happened with xrpl-py?**
The Python SDK had a silent data corruption bug in its support for two upcoming features — the Lending Protocol and Dynamic Multi-Purpose Tokens. A field in the binary serialization map was pointing to the wrong slot (code 54 instead of 53), meaning Python-constructed transactions for these features would have been encoded incorrectly and likely rejected by the network. This was caught before those features are enabled on mainnet, and the fix is already merged.

**What should validators pay attention to?**
A bug report (not yet confirmed on rippled, but reproduced on the related Xahau network) suggests that nodes running older software that have been blocked from the latest amendments may crash when they receive certain newer-format data during a ledger synchronization event. If you operate a validator, keep an eye on issue [#6492](https://github.com/XRPLF/rippled/issues/6492) for updates. For ongoing developments, follow @XRPLF and @RippleXDev on X.

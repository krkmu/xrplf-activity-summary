# XRPL Developments Weekly Summary: 2026-02-28 to 2026-03-07

## Headline
The `server_definitions` RPC endpoint gained a long-requested enhancement this week: transaction and ledger entry formats are now included in its response, closing a two-year-old issue. Meanwhile, a bug fix in xrpl-py corrected serialization field codes for DynamicMPT and Lending Protocol that could have corrupted transactions on the write path.

## What Shipped

### Protocol & API

**`server_definitions` now includes transaction formats and flags** — [rippled#6321](https://github.com/XRPLF/rippled/pull/6321)
After more than two years open, issue [#5151](https://github.com/XRPLF/rippled/issues/5151) is resolved. The `server_definitions` RPC response now includes transaction and ledger entry formats, as well as flags — closing the long-standing gap that required client libraries (like Xaman/Xumm) to hard-code or manually maintain these values. This is a meaningful improvement for any client implementation that dynamically decodes XRPL transactions without hard-coding field definitions. Labeled **API Change**.

**`gateway_balances` now skips MPT entries correctly** — [rippled#6143](https://github.com/XRPLF/rippled/pull/6143)
The `gateway_balances` RPC, which only applies to IOUs, previously didn't account for MPT-type entries. This fix correctly skips MPT entries to avoid incorrect output. Labeled **API Change**.

**Defensive sfData length check for EscrowFinish (Smart Escrow)** — [rippled#6449](https://github.com/XRPLF/rippled/pull/6449)
A defensive size guard was added in `EscrowFinish::doApply()` to ensure WASM-produced data fields do not exceed the protocol's maximum allowed length before being written to the ledger.

**xrpl-py: Critical binary codec field corrections** — [xrpl-py#918](https://github.com/XRPLF/xrpl-py/pull/918)
Two incorrect SField entries in xrpl-py's `definitions.json` were corrected:
- `sfMutableFlags` (DynamicMPT) was encoded as field code 54 instead of 53, which would cause xrpl-py to serialize `MutableFlags` using the field code rippled assigns to `sfStartDate` — silently corrupting transactions.
- `PreviousPaymentDate` was renamed to `PreviousPaymentDueDate` and `LoanScale` entries were reorganized.
Developers building with xrpl-py against DynamicMPT or Lending Protocol features should update promptly.

## Plain English Summary

This week saw a long-overdue improvement to how XRPL nodes describe themselves to software developers. The `server_definitions` API call — which wallets, libraries, and developer tools use to understand what transaction types and fields the ledger supports — now includes detailed format information like transaction field types, ledger entry structures, and flag values. Previously, developers building wallets or signing tools had to hard-code this information themselves or maintain their own copies. With this change merged ([rippled#6321](https://github.com/XRPLF/rippled/pull/6321)), any compatible tool can retrieve that information directly from the node. This makes it easier to build software that works correctly across different network versions, including devnets and custom deployments.

A more urgent change shipped in the xrpl-py Python library ([xrpl-py#918](https://github.com/XRPLF/xrpl-py/pull/918)): two serialization field codes were incorrect in the library's internal definitions for the DynamicMPT and Lending Protocol features. Specifically, when building transactions involving `MutableFlags`, xrpl-py was encoding the data using the wrong field slot — the same slot rippled uses for `StartDate`. This would silently produce malformed transactions. Developers using xrpl-py to interact with DynamicMPT or Lending Protocol functionality should update to the latest version.

Validators and node operators should also be aware of an open bug report ([rippled#6492](https://github.com/XRPLF/rippled/issues/6492)) indicating that amendment-blocked nodes — nodes that have fallen behind on enabled amendments — may crash when the network makes a large ledger sequence jump and the node tries to process transactions containing fields it doesn't recognize. This crash mode was reproduced on a related project (Xahau) but has not yet been confirmed on rippled itself. A fix is being tracked. If you run an amendment-blocked node for any reason, this is worth watching.

For more details: [rippled#6321](https://github.com/XRPLF/rippled/pull/6321) · [xrpl-py#918](https://github.com/XRPLF/xrpl-py/pull/918) · [rippled#6492](https://github.com/XRPLF/rippled/issues/6492). Follow @XRPLF and @RippleXDev on X for ongoing updates.

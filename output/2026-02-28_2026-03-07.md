# XRPL Developments Weekly Summary: 2026-02-28 to 2026-03-07

## Headline

The `server_definitions` RPC endpoint gained transaction and ledger entry formats and flags this week with the merge of [rippled#6321](https://github.com/XRPLF/rippled/pull/6321), closing a long-standing request and enabling client libraries to handle serialization more independently. Simultaneously, a broad code quality push landed across rippled and Clio — new clang-tidy checks, CMake tooling upgrades, and a major internal transaction folder restructure — while xrpl-py fixed a serialization-corrupting field-code mismatch affecting Lending Protocol and Dynamic MPT transactions.

## Plain English Summary

**What changed and why it matters for developers**

The biggest developer-facing change this week is that the `server_definitions` API endpoint — which nodes expose to help wallets and libraries understand the ledger format — now includes transaction and flag definitions. Previously, developers building XRPL client software had to maintain a separate, hardcoded list of transaction types, ledger entry formats, and flag values alongside the node's data. Now that information comes directly from the node itself, making it much easier to build tools that work across devnet, testnet, and mainnet without manual updates. This closes a GitHub issue that had been open since 2024 and was one of the more frequently requested developer experience improvements.

**A serialization bug was fixed in the Python library**

The xrpl-py library had incorrect field codes for two newer protocol features — the Lending Protocol and Dynamic Multi-Purpose Tokens. When software serializes a transaction (converts it to the binary format the network uses), it relies on these codes to label each field correctly. The wrong codes meant that certain fields were mislabeled in a way that silently overwrote unrelated fields, corrupting transactions before they even reached the network. This has been corrected in [xrpl-py#918](https://github.com/XRPLF/xrpl-py/pull/918). Anyone building applications with xrpl-py against the Lending Protocol or Dynamic MPT features should update to the fixed version.

**Node operators: a Clio startup fix and a bug to watch**

Clio (a read-optimized API server for XRPL) had a regression that caused it to fail to start if no cache file existed on disk — for example, on a fresh deployment. That is now fixed in [clio#2976](https://github.com/XRPLF/clio/pull/2976). Separately, a bug report ([rippled#6492](https://github.com/XRPLF/rippled/issues/6492)) suggests that nodes running older software that have been blocked by amendments — a normal state where a node refuses to follow the network until it upgrades — may crash when the network skips ahead during what is called an LCL JUMP. This was reproduced on a related network (Xahau) but has not yet been confirmed on the main XRPL node software. No action is required today, but validators and node operators should watch that issue for updates. Follow @XRPLF and @RippleXDev on X for timely announcements.

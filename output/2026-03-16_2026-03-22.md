# XRPL Developments Weekly Summary: March 16–22, 2026

## TL;DR

This week saw a heavy wave of code quality improvements in rippled (merged to develop), including a large code generator for transaction and ledger entry types (+59,363 lines), continued clang-tidy hardening across hundreds of files, and fixes to the Permission Delegation (XLS-75) implementation. In Clio (the API server), a meaningful reliability fix merged: nodes can now automatically recover from the "fallback" writer state — an item tracked as "In Progress" last week. In the XRPL-Standards repo, the XLS number assignment process was hardened to prevent bot race conditions and unauthorized assignment.

## What Merged

### Protocol & Feature Development (rippled — merged to develop)

**Permission Delegation fix: disallow empty permission list without existing Delegate object** ([rippled#6542](https://github.com/XRPLF/rippled/pull/6542), +55/−31 across 2 files) — Fixes a logic error in `DelegateSet` (XLS-75): if no Delegate object exists on the account, an empty permission list should be rejected at `preclaim`. An empty list is only valid when deleting an *existing* Delegate object. Also ensures an empty permission list in `doApply` now returns `tecINTERNAL` as expected instead of silently continuing.

**`sfBlindingFactor` type updated to `uint256`** ([rippled#6565](https://github.com/XRPLF/rippled/pull/6565), +108/−111 across 10 files) — Updates the blinding factor field used in the in-development Confidential MPT (XLS-96) work, and refactors helper functions to return `std::optional`. Part of the ongoing confidential transfer audit remediation.

**Confidential MPT: privacy flag and public key field renames** ([rippled#6550](https://github.com/XRPLF/rippled/pull/6550), +233/−220 across 18 files) — Renames encryption-related SFields and transaction flags for clarity (e.g. `sfIssuerElGamalPublicKey` → `sfIssuerEncryptionKey`). The companion spec update merged in XRPL-Standards this week (see Standards section below). Still in development, not yet open for voting.

**`LendingProtocolV1_1` amendment renamed from fix to feature macro** ([rippled#6527](https://github.com/XRPLF/rippled/pull/6527), +13/−13 across 4 files) — Corrects the macro from `XRPL_FIX` to `XRPL_FEATURE` since `LendingProtocolV1_1` is a feature amendment, not a bug fix. Affects `VaultDelete` and related tests.

**Peer Crawler API: `port` field type inconsistency fixed** ([rippled#6318](https://github.com/XRPLF/rippled/pull/6318), +10/−3 across 3 files, closes [#5029](https://github.com/XRPLF/rippled/issues/5029)) — The peer crawler API was returning `port` as a string for outbound peers but as an integer for inbound peers since the original implementation (PR #1017). Now always returns as an integer. Also moves inline string literals `"active"`, `"in"`, `"out"` to `jss.h`. Approved by a core team reviewer. Note: this is a minor API change to a peer-port endpoint, not the standard API, so versioning concerns do not apply.

**NFT: assorted flag fixes** ([rippled#6566](https://github.com/XRPLF/rippled/pull/6566), +7/−6 across 3 files) — Fixes a couple of incorrect flag references (same value, wrong variable — no amendment needed) spotted via AI review.

**DID: assorted fixes and dead test recovery** ([rippled#6552](https://github.com/XRPLF/rippled/pull/6552), +8/−6 across 5 files) — Makes `addSLE` in `DIDSet` a static function, renames `Attestation` to `Data` everywhere, and fixes tests that were defined but never included in the test runner.

**Escrow: remove dead code in helper logic** ([rippled#6553](https://github.com/XRPLF/rippled/pull/6553), +3/−4 in 1 file) — Removes a dead code path and redundant variable, spotted via AI review.

### Code Generator (rippled — merged to develop)

**Code generator for transactions and ledger entries** ([rippled#6443](https://github.com/XRPLF/rippled/pull/6443), +59,363/−5 across 237 files) — Adds an autogeneration step that produces typed C++ classes for every transaction and ledger entry from a canonical schema. This is the largest single merge this week by line count and represents a significant infrastructure investment: typed ledger entries can now be used in downstream code without manual boilerplate, and future transaction types can be added with less per-entry work. An external contributor submitted this, with active discussion ongoing about how to extend these types with non-autogenerated methods.

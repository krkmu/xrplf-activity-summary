# XRPL Developments Weekly Summary: Feb 23 – Mar 1, 2026

## TL;DR
rippled 3.1.1 shipped as a hotfix disabling the Batch (XLS-56) and fixBatchInnerSigs amendments following a disclosed logic flaw in signature validation. ## What Shipped

### Protocol: Batch (XLS-56) Formally Disabled — Action Required for Validators

**rippled 3.1.1** ([release](https://github.com/XRPLF/rippled/releases/tag/3.1.1)) is now live. The key change: both the `Batch` and `fixBatchInnerSigs` amendments are marked `Supported::no`, preventing them from activating on any network.

A vulnerability disclosure report published on February 26 ([xrpl.org/blog/2026/vulnerabilitydisclosurereport-bug-feb2026](https://xrpl.org/blog/2026/vulnerabilitydisclosurereport-bug-feb2026)) explains the root cause: a logic flaw in signature validation that could allow an attacker to execute inner transactions on behalf of arbitrary accounts without their private keys. The amendment was in its voting phase and had not activated on mainnet, so no funds were at risk.

**Validators and node operators should upgrade to 3.1.1.** A corrected replacement amendment (`BatchV1_1`) is under development but has no release date yet. Additionally, Devnet was reset on March 3 to prevent validators running 3.1.1 from becoming amendment-blocked. GPG signing keys for rippled packages have also been rotated — see [xrpl.org/blog/2026/gpg-key-rotation](https://xrpl.org/blog/2026/gpg-key-rotation) for details on updating your package verification.

The hotfix changes were cherry-picked back into `develop` via [rippled#6417](https://github.com/XRPLF/rippled/pull/6417) to ensure they are included in the next release.

### Performance: Explicit Heap Trimming on Linux

[rippled#6022](https://github.com/XRPLF/rippled/pull/6022) merges a `MallocTrim` helper that calls `malloc_trim(0)` after cache sweeps on Linux/glibc systems. This returns unused heap pages to the OS after memory-intensive operations, addressing a known pattern of memory growth in long-running nodes. The change has been tested in a performance lab and on Mainnet. Non-Linux builds are unaffected. A blog post summarizing the results is in preparation.

### Protocol: Vault and Lending Work Continues

[rippled#6356](https://github.com/XRPLF/rippled/pull/6356) adds an optional `Data` (memo) field to `VaultDelete` transactions, allowing issuers to record a reason for deletion — per [XRPL-Standards#470](https://github.com/XRPLF/XRPL-Standards/pull/470). This is part of the ongoing Single Asset Vault (XLS-65) implementation.

[rippled#6444](https://github.com/XRPLF/rippled/pull/6444) updates the hashing scheme for an in-development transaction type and adds ticket support, changing the hash formula to `TxType || Account || IssuanceID || SequenceOrTicket`.

The **XLS-66 Lending Protocol** specification ([XRPL-Standards#240](https://github.com/XRPLF/XRPL-Standards/pull/240)) was merged into the standards repo. Merging at the spec level indicates the document is ready for editing and development tracking — it does not imply the protocol change is final or endorsed.

## Plain English Summary

**The Batch feature has been pulled — here's what that means.** A bug was found in the Batch amendment, which was a proposed feature that would have let users bundle multiple transactions together in a single submission. Researchers discovered that the signature-checking logic had a flaw that could have allowed an attacker to execute transactions on behalf of other users without their private keys. Because Batch hadn't yet activated on the main network, no accounts or funds were at risk. The rippled 3.1.1 release formally switches this feature off so it can't accidentally turn on. Validators and node operators running rippled 3.1.0 should upgrade to 3.1.1. The development team is working on a corrected version called `BatchV1_1`, but it has no release date yet. More details at [xrpl.org/blog/2026/rippled-3.1.1](https://xrpl.org/blog/2026/rippled-3.1.1) and the full disclosure at [xrpl.org/blog/2026/vulnerabilitydisclosurereport-bug-feb2026](https://xrpl.org/blog/2026/vulnerabilitydisclosurereport-bug-feb2026).

**Nodes on Linux will use less memory over time.** A change was merged that instructs the operating system to reclaim unused memory more aggressively after the node finishes its regular cleanup cycles. Over days and weeks of continuous operation, this should reduce the amount of RAM a node occupies on Linux servers — potentially lowering hosting costs for operators running resource-constrained hardware. This change only applies to Linux systems using the standard glibc memory allocator; other operating systems are unaffected.

**The XRPL developer documentation got a noticeable upgrade.** The tutorials section of xrpl.org has a new, organized landing page that groups tutorials by topic and shows which programming languages each one covers. Code tabs across the site now stay in sync — click "Python" on one section and all other tabs on the page (and future pages you visit) switch to Python too, remembered in your browser. The Batch-related documentation has been updated to reflect its disabled status, and a vulnerability disclosure page has been published. Python developers using the xrpl-py library should note that Python 3.8 is no longer supported — the library now requires Python 3.9 or newer. Follow [@XRPLF](https://x.com/XRPLF) and [@RippleXDev](https://x.com/RippleXDev) for ongoing updates.

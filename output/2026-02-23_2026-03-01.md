### Protocol & Amendment Response
**rippled 3.1.1 released** — This hotfix release marks both `Batch` (XLS-56) and `fixBatchInnerSigs` as `Supported::no`, preventing them from activating on any network. A [full vulnerability disclosure](https://xrpl.org/blog/2026/vulnerabilitydisclosurereport-bug-feb2026) published Feb 26 explains the root cause: a logic flaw in signature validation allowed an attacker to execute inner transactions on behalf of arbitrary accounts without their private keys. The amendment was in its voting phase and had **not** activated on mainnet; no funds were at risk. A corrected replacement amendment (`BatchV1_1`) is under development with no set release date. Validators and node operators should upgrade to 3.1.1 immediately. ## Plain English Summary

**rippled 3.1.1: Batch amendment disabled**

The most important development this week is the release of rippled 3.1.1, the reference server software for the XRP Ledger. A security researcher and an AI security tool discovered a serious flaw in a new feature called the Batch amendment — which was designed to let users bundle multiple transactions together in one go. The flaw meant an attacker could have executed transactions on behalf of other users without ever having their private keys, effectively stealing funds. Importantly, the feature had not yet been switched on for mainnet, so no real funds were ever at risk. The 3.1.1 release disables both the Batch amendment and a related fix amendment, preventing them from ever being activated with the known flaw. Validators and node operators should upgrade to 3.1.1 immediately. A corrected version of Batch (called BatchV1_1) is being worked on, but has no release date yet. Devnet — the public test network — was also reset on March 3 to clean up the state left by the disabled amendment; if you have Devnet test accounts you will need to re-create them and get fresh test XRP from the faucet. Full technical details are available in the [vulnerability disclosure report](https://xrpl.org/blog/2026/vulnerabilitydisclosurereport-bug-feb2026) and the [3.1.1 release blog](https://xrpl.org/blog/2026/rippled-3.1.1).

**Memory improvements and code health in rippled**

Separately from the hotfix, work continues on the `develop` branch of rippled (meaning changes that are merged but not yet released to the network). A notable improvement this week adds a mechanism to explicitly release unused memory back to the operating system on Linux servers after periodic cleanup cycles. Long-running nodes tend to accumulate memory over time even after freeing internal data structures; this change helps address that, potentially lowering hosting costs for node operators. Another batch of improvements refactored rippled's internal safety-check system (InvariantCheck) from one large file into ten smaller, focused modules — making the codebase easier to maintain and extend. Neither change is live on mainnet yet.

**Documentation, SDKs, and standards**

The XRPL developer documentation site got a significant update this week: the tutorials landing page was redesigned with a curated, categorized layout and auto-detected programming language icons, and code tabs across pages now sync automatically (pick "Python" once and all tabs on the page switch to Python). The Python SDK (xrpl-py) dropped support for Python 3.8, which reached end-of-life in October 2024 — developers using xrpl-py now need Python 3.9 or newer. On the standards side, the XLS-66 Lending Protocol specification was formally merged into the XRPL-Standards repository, marking a milestone for the DeFi lending feature currently open for voting on the network. For ongoing updates, follow @XRPLF and @RippleXDev on X.

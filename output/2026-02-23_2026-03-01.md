## What Merged

### Protocol: Batch Disabled, 3.1.1 Released
[rippled 3.1.1](https://github.com/XRPLF/rippled/releases/tag/3.1.1) is the headline of the week. The release marks both the `Batch` (XLS-56) and `fixBatchInnerSigs` amendments as `Supported::no`, preventing them from activating. This follows the February 19 report by Pranamya Keshkamat and Cantina AI of a logic flaw in Batch's signature-validation logic that could have allowed unauthorized execution of inner transactions on behalf of arbitrary accounts — including fund transfers — without the victim's private keys. The amendment had not activated on mainnet, so no funds were at risk. The full technical details are in the [vulnerability disclosure report](https://xrpl.org/blog/2026/vulnerabilitydisclosurereport-bug-feb2026).

[rippled#6417](https://github.com/XRPLF/rippled/pull/6417) cherry-picked the 3.1.1 hotfix changes (disabling Batch and fixBatchInnerSigs) back into `develop`, ensuring the fix carries forward to all future releases.

**Action required for validators and operators:** Upgrade to rippled 3.1.1. A corrected replacement amendment, `BatchV1_1`, is under development but has no set release date. Devnet was reset on March 3, 2026 to prevent amendment-blocking on nodes that upgraded.

Also note: Ripple has rotated the GPG key used to sign `rippled` packages. See the [blog post](https://xrpl.org/blog/2026/rippled-3.1.1) and update your package verification setup.

### Performance: Heap Trimming on Linux Nodes
[rippled#6022](https://github.com/XRPLF/rippled/pull/6022) (merged to `develop`) introduces a `MallocTrim` helper that explicitly calls `malloc_trim(0)` on Linux/glibc systems after each cache sweep. This returns freed heap pages to the OS rather than letting the allocator hold onto them, addressing a known memory growth pattern in long-running nodes. The change is a no-op on non-Linux builds. Internal testing on Mainnet has been conducted; a blog post summarizing results is forthcoming.

## Plain English Summary

**The big news: a bug in the Batch feature, and a fast fix**

This week's most important development is the release of rippled 3.1.1. "Batch" (formally XLS-56) is a feature that would let users bundle multiple XRPL transactions together into a single atomic group — if any one fails, they all fail. A bug was discovered in how the feature validates signatures: a flaw in the logic could have let an attacker execute transactions on behalf of other accounts without those accounts' private keys, potentially stealing funds or changing ledger state. The bug was caught before the Batch feature was ever turned on for the main network, so no real funds were affected. However, because the code existed in an earlier software version (3.1.0), the response was swift: a new version, 3.1.1, was released within days, fully disabling Batch until a corrected version is ready. **Validators and node operators should upgrade to 3.1.1 as soon as possible.** Also, Ripple has changed the cryptographic signing key used to verify rippled software packages — operators who verify package signatures will need to update their key. The full technical write-up of the bug is available at https://xrpl.org/blog/2026/vulnerabilitydisclosurereport-bug-feb2026.

**Under the hood: better memory management for node operators**

A meaningful infrastructure improvement was merged to the `develop` branch this week (meaning it is not yet live — it will ship in a future release). Long-running XRPL nodes on Linux systems tend to accumulate memory over time because the system doesn't always return freed memory to the operating system after it cleans its internal caches. The new change explicitly instructs the Linux memory allocator to release unused memory pages back to the OS after each cleanup cycle. In practical terms, this means node operators may see lower and more stable RAM usage on their servers over time, potentially reducing hosting costs. Internal testing on Mainnet has been completed; a public blog post with benchmark results is coming.

**Docs, SDKs, and the Lending spec**

The XRPL developer documentation site received significant attention this week. Setup scripts for DeFi tutorials were updated to avoid relying on the now-disabled Batch feature. A new sync feature means clicking a language tab (e.g., "JavaScript" or "Python") on the docs site now updates all tabs on the page and remembers your preference for future visits. The XLS-66 Lending Protocol draft specification — which defines how lending could work natively on the XRP Ledger — was formally merged into the standards repository, making it easier for contributors to iterate on. For Python developers: xrpl-py has dropped support for Python 3.8, which reached its end-of-life in 2024; you'll need Python 3.9 or newer going forward.

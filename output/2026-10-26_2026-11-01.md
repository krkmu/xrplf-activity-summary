## Plain English Summary

This week's XRP Ledger development was dominated by documentation improvements and preparation for upcoming changes. The developer website (xrpl.org) received its largest batch of updates in the comparison period — 23 pull requests merged — addressing everything from correcting outdated information to patching security vulnerabilities in the site's underlying software libraries. For anyone building on XRPL, the most notable content change was updating the Permissioned Domains page: it previously said Permissioned DEXes were "in development," but since this feature is now live on Mainnet, the docs now accurately reflect that. Several other corrections landed too, including clarifying that enabling confidential token balances after token creation requires an additional protocol amendment (DynamicMPT), and fixing an incorrect claim that a particular account setting couldn't be turned off.

On the JavaScript SDK side, two beta versions were published — `xrpl@5.4.0-beta.0` and `ripple-binary-codec@2.12.0-beta.0`. The main xrpl package beta fixes issues with Batch transactions (the feature that lets users bundle multiple transactions together): it now correctly allows `LastLedgerSequence` in inner transactions and properly requires sponsor signatures. These are beta releases, so they're available for testing but not yet recommended for production applications. Separately, the library's WebSocket connection code now protects against a scenario where a server could inject messages that mimic internal events — a defensive improvement that will ship in the next stable npm release.

Behind the scenes in the core server code (rippled), while only two minor PRs merged this week, a wave of 26 new pull requests were opened — most from the same developer working through a systematic robustness review. These changes add safety checks and bounds throughout the system: capping how much data a node sends in peer replies, limiting the size of data structures, ensuring all pending operations complete cleanly during shutdown, and fixing cache statistics that weren't being tracked correctly. None of these change how the network behaves — they make the server software more resilient against edge cases. These will be reviewed and start merging in the coming weeks, eventually reaching node operators in a future release.

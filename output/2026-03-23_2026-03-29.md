# XRPL Developments Weekly Summary: March 23–29, 2026

## TL;DR
A busy week across the ecosystem: in rippled, 27 PRs merged to develop including on-chain verification via the mpt-crypto SDK, a placeholder amendment for assorted bug fixes, multiple Lending Protocol refinements, and a major ledger modularization refactor. The Java SDK (xrpl4j) shipped a significant `SignatureUtils` refactoring that eliminates large switch statements in the transaction signing API. On the developer portal, a new "Delete an Account" tutorial with JavaScript/Python samples merged alongside Go code samples for the Lending Protocol. On opensource.ripple.com, reference and concept documentation for Confidential Transfers (XLS-96) was published. A vulnerability disclosure blog post was also published detailing two liveness bugs fixed in rippled 3.0.0.

## Community & Discussions

**Vulnerability Disclosure: Transaction Set Handling** — A [blog post](https://xrpl.org/blog/2026/vulnerabilitydisclosurereport-bug-mar2026) was published this week describing two liveness vulnerabilities discovered by **Nikolaos Kamarinakis** from **Common Prefix**, reported June 9, 2025. Both bugs could have allowed a compromised UNL validator to crash other validators by manipulating transaction data in transaction sets. Fixes were included in rippled 3.0.0. No action is needed by operators running 3.0.0 or later.

**Validator Graceful Handoff proposal** — A new pre-standard proposal discussion ([XRPL-Standards#505](https://github.com/XRPLF/XRPL-Standards/discussions/505)) proposes a `tmHandoff` peer protocol message and warm-standby process mode for rippled. The goal: enable validators to signal a planned, time-bounded absence to peers before going offline, allowing near-zero-downtime software upgrades. Early discussion stage.

**Community contributors active across rippled** — Multiple contributors were active this week: @pratikmankawde submitted fixes for coroutine and WebSocket issues, @a1q123456 landed the ledger modularization and ServiceRegistry naming consistency changes, @mathbunnyru contributed dependency updates and CI improvements, @vlntb shortened job names, and @shortthefomo has open PRs for pathfinding improvements and RWDB backporting.

**RemoveEmptyHolding / MPToken deletion with active escrow** ([rippled#6635](https://github.com/XRPLF/rippled/pull/6635)) — Community member @Kassaking7 submitted a fix to prevent deletion of MPTokens that have a locked amount (e.g., from an active escrow). The PR went through multiple rounds of review, including a request to amendment-gate the change since the affected code has already shipped. Discussions are ongoing about batching this fix with the `fixSecurity3_1_3` amendment. Initially received CHANGES_REQUESTED, now APPROVED by a core team reviewer.

**New rippled issues filed** — Multiple new issues were filed this week, all by core team collaborator @mvadari and tagged "AI Triage": [#6666](https://github.com/XRPLF/rippled/issues/6666) (missing `isPseudoAccount` check in IOU/MPT payment paths), [#6665](https://github.com/XRPLF/rippled/issues/6665) (stale OrderBookDB entries after AMMDelete), [#6664](https://github.com/XRPLF/rippled/issues/6664) (AMMVote writes to expired auction slot), [#6663](https://github.com/XRPLF/rippled/issues/6663) (AMMDelete preflight performs no validation), [#6662](https://github.com/XRPLF/rippled/issues/6662) (AccountDelete needs explicit AMM guard), [#6661](https://github.com/XRPLF/rippled/issues/6661) (add defensive assert in `ammAssetOut`), [#6660](https://github.com/XRPLF/rippled/issues/6660) (add defensive assert for `minTokens`), [#6659](https://github.com/XRPLF/rippled/issues/6659) (NFTokenBurn should reject when issuer SLE is absent). These are defense-in-depth and technical debt items — not confirmed vulnerabilities.

**Feature requests** — Two feature requests from community member @Platonenkov: [#6629](https://github.com/XRPLF/rippled/issues/6629) proposes enriching `account_currencies` with issuer entries and trust line state, and [#6625](https://github.com/XRPLF/rippled/issues/6625) reports that `book_offers` pagination doesn't reliably return a `marker`.

**xrpl-py: IOU value precision bug** ([xrpl-py#923](https://github.com/XRPLF/xrpl-py/issues/923)) — Community member @sublimator reported that `verify_iou_value` incorrectly rejects valid IOU values with large exponents (e.g., `9999999999999999e79`) because `_calculate_precision()` counts all digits of the expanded decimal form rather than just the 16 significant figures.

## Plain English Summary

This was a productive week across the XRP Ledger development ecosystem. The most notable change in rippled (the core server software, merged to its development branch but not yet live) was the integration of a dedicated cryptographic SDK for on-chain verification. Previously, the verification logic was spread across the codebase; now it uses a single library, which actually removed more code than it added — a sign of cleaner, more maintainable design. Alongside this, a contributor completed a substantial reorganization of the ledger module, splitting it into more manageable pieces across 93 files. Several bug fixes for the Lending Protocol and Vault features (which let users create vaults for lending and borrowing) were also prepared, gated behind a new amendment that must be voted on by validators before taking effect. These fixes address edge cases like being able to withdraw more assets than actually available, or exceeding token issuance limits during multi-send operations.

For developers building on the XRP Ledger, this was a standout week. The Java SDK (xrpl4j) eliminated hundreds of lines of repetitive code in its transaction signing system by using auto-generated type-safe methods — meaning Java developers get cleaner APIs and fewer potential bugs when signing transactions.

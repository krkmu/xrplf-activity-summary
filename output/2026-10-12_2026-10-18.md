# XRPL Developments Weekly Summary: October 12–18, 2026

## TL;DR
An exceptionally active week with 93 PRs merged across 6 repos. In **rippled**, 68 PRs merged to develop — the standout work includes the complete FixedPrecision Vault stack (6 PRs introducing cash-basis accounting for the Lending Protocol), Smart Escrow transaction field handling and fee voting, a large SHAMap robustness stack (8 PRs), the `Number` type shrinking from 24 to 16 bytes, and the retirement of the `fixAMMv1_1` amendment. In **Clio**, 16 PRs merged including `mpt_issuances` subscription support and a timeout cancellation bug fix. In **xrpl4j**, 4 PRs merged fixing `ServerSecret` byte zeroing and `AffectedNode` serialization round-tripping. The **developer portal** merged 4 PRs correcting MPT, Batch, and LoanPay reference docs. **xrpl-py** published beta **v5.3.0b0**.

### Protocol & Feature Work (rippled — merged to develop)

- **Complete FixedPrecision Vault stack (6 PRs)**: The full Lending Protocol V1.2 FixedPrecision Vault feature landed this week as a coordinated 6-part stack, introducing cash-basis (principal-only) accounting for Vaults. The stack includes: grid and balance helpers ([rippled#8257](https://github.com/XRPLF/rippled/pull/8257), +2,167/−91), Vault transactors and invariants ([rippled#8460](https://github.com/XRPLF/rippled/pull/8460), +2,474/−367), LoanBroker cover rounding ([rippled#8258](https://github.com/XRPLF/rippled/pull/8258), +868/−104), LoanSet through AssetsDeployed ([rippled#8260](https://github.com/XRPLF/rippled/pull/8260), +2,135/−195), LoanPay and LoanManage ([rippled#8271](https://github.com/XRPLF/rippled/pull/8271), +5,871/−355), and LoanManage default and impairment ([rippled#8461](https://github.com/XRPLF/rippled/pull/8461), +2,199/−223). All labeled `feature: LP1.2`.

- **Smart Escrow transaction field handling**: [rippled#8215](https://github.com/XRPLF/rippled/pull/8215) (+1,375/−41) — Adds validation rules, fee calculations, and reserve accounting for `EscrowCreate.Bytecode`/`Data` and `EscrowFinish.Gas`, gated on `featureSmartEscrow`. This PR does **not** run WASM bytecode — the engine is not yet on develop.

- **Smart Escrow fee voting**: [rippled#8214](https://github.com/XRPLF/rippled/pull/8214) (+1,432/−80) — Adds `GasLimit`, `BytecodeSizeLimit`, and `GasPrice` as votable network fee settings, gated on `featureSmartEscrow`.

- **TransactionProposalCancel & Cosign Ticket reservation (XLS-103)**: [rippled#8538](https://github.com/XRPLF/rippled/pull/8538) (+3,987/−42) — Adds the `TransactionProposalCancel` transaction type and Ticket reservation for the On-Chain Cosigner feature. *(Was "In Progress" last week — now merged.)*

- **TransactionProposal invariants for Cosign**: [rippled#8130](https://github.com/XRPLF/rippled/pull/8130) (+932/−8) — Adds `ValidTransactionProposal`, a global invariant enforcing creation/modification/deletion rules for `TransactionProposal` ledger entries.

- **IssuerMirrorEncryptionKey and InitialIssuerEncryptionKey**: [rippled#8325](https://github.com/XRPLF/rippled/pull/8325) (+380/−18) — Adds support for these fields and unit tests.

- **Retire fixAMMv1_1 amendment**: [rippled#8226](https://github.com/XRPLF/rippled/pull/8226) (+693/−1,667) — Moves `fixAMMv1_1` to the retired list and deletes its conditional code paths, keeping only the enabled behavior. Net reduction of ~1,000 lines.

## Plain English Summary

This was one of the most active development weeks for the XRP Ledger, with 93 changes merged across the ecosystem. The biggest story is the complete landing of "FixedPrecision Vaults" — a six-part stack that introduces a new accounting model for the Lending Protocol. In plain terms, when the Lending Protocol eventually goes live, vault operators will be able to use "cash-basis" accounting where interest is recognized only when actually paid, rather than when it accrues. This is important for financial accuracy and regulatory alignment. The full stack — covering vault creation, deposits, withdrawals, loan setup, loan payments, and loan defaults — all merged to the development branch this week.

Smart Escrows (a feature that would let users attach small programs to escrow transactions) made significant progress: the code now validates and prices the three key fields (program code, data, and computational budget) and adds new votable network settings so validators can collectively set limits on contract size and cost. The programs can't actually run yet — the execution engine hasn't been merged to the main development branch — but the transaction structure and fee framework are now in place. Separately, the core data structure that nodes use to synchronize ledger state with each other (called a SHAMap) received eight fixes in a systematic hardening effort: nodes now detect and reject invalid data more reliably during synchronization, prevent race conditions in background threads, and refuse to mark corrupted data as permanent. For node operators, this means better resilience against malformed peer data once a release ships. The `Number` type used throughout the transaction engine was also shrunk from 24 to 16 bytes by simply reordering its internal fields — a zero-cost memory saving that touches every calculation the server makes. On the SDK side, the Java library (xrpl4j) fixed a bug where a security-related class (`ServerSecret`) was accidentally zeroing the caller's own secret bytes instead of its own copy, and fixed a serialization round-trip bug with transaction metadata. The Python SDK (xrpl-py) published a beta release (v5.3.0b0) that drops Python 3.8 support and includes earlier fixes. The Clio API server now supports subscribing to MPT issuance events, and the developer portal corrected several reference documentation errors in the MPT, Batch, and Lending Protocol pages.

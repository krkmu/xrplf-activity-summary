[rippled#6321](https://github.com/XRPLF/rippled/pull/6321) — merged to `develop` after closing long-standing issue [#5151](https://github.com/XRPLF/rippled/issues/5151) — adds transaction and ledger entry formats, field definitions, and flags to the `server_definitions` RPC response. ## Plain English Summary

**What developers will notice most: richer node introspection**

The most developer-facing change merged this week (to the `develop` branch — not yet live on the network) is an expansion of what nodes tell you about themselves. The `server_definitions` API response — a machine-readable description of the XRPL protocol — now includes the complete list of transaction types, the fields each transaction accepts, valid flags, and ledger entry formats. Previously, developers building wallets, explorers, or client libraries had to hardcode this information or maintain their own copies. Now, a client can ask any node and get the full picture. This was a feature request that had been open for years and is tracked by the XLS-97 specification. It means wallet and tooling developers can more easily build generic transaction-handling code that automatically adapts as new features are added to the protocol.

**A data corruption bug fixed in the Python SDK**

A subtle but important fix landed in xrpl-py this week. The Python library's internal "binary codec" — the component that translates Python objects into the binary format the XRP Ledger understands — had incorrect definitions for two fields used by the upcoming Lending Protocol and Dynamic MPTs features. One field (`MutableFlags`) was mapped to the wrong code number, meaning any Python code serializing a Lending Protocol transaction would silently write the wrong data. The fix corrects these mappings. If you're a Python developer testing Lending Protocol transactions on devnet, you should update xrpl-py. The affected features are not yet live on mainnet, so this only affects devnet testing today.

**A bug to watch: amendment-blocked validators may crash**

A community contributor discovered and reported a potential crash scenario for XRPL validator nodes. Specifically, nodes that are running older software and have been "blocked" from activating new amendments may crash when the network advances to a ledger containing transaction types those nodes don't recognize. This is a situation that naturally occurs whenever a new protocol feature activates on the network and some validators haven't upgraded yet. The bug was reproduced on Xahau (a network that shares some codebase with rippled) but hasn't been confirmed on rippled directly. The team is tracking a fix. Validators that routinely upgrade promptly are not affected by this risk, but it's worth watching if you operate infrastructure that sometimes lags behind software updates.

# XRPL Developments Weekly Summary: Mar 2 – Mar 8, 2026

## TL;DR
The `server_definitions` RPC got a major upgrade this week — transaction formats, ledger entry formats, and flags now ship directly from the node, closing a 2-year-old request. Separately, xrpl-py fixed a serialization-corrupting field code mismatch for DynamicMPT and Lending Protocol types, and the xrpl-dev-portal received a substantial tutorials information architecture overhaul.

## What Shipped

### Protocol & API

**`server_definitions` now includes Formats and Flags** — [rippled#6321](https://github.com/XRPLF/rippled/pull/6321) (+1169/-503 across 29 files) closes [rippled#5151](https://github.com/XRPLF/rippled/issues/5151), a request that has been open since 2024. The `server_definitions` response now includes transaction and ledger entry format descriptors alongside flags, letting client libraries fully derive serialization and flag semantics from a live node rather than hardcoding them. This is the implementation of XLS-97 (Formats, Fields and Flags), whose spec was merged last week. The closed issue [rippled#5506](https://github.com/XRPLF/rippled/issues/5506) (`server_definitions should include DeliverMax`) was also resolved as part of this work.

**API Change: `gateway_balances` with MPT** — [rippled#6143](https://github.com/XRPLF/rippled/pull/6143) (+44/-1, labeled `API Change`) fixes the `gateway_balances` RPC to skip MPT-type balances rather than erroring. The RPC is IOU-specific; the fix ensures MPT entries are silently excluded rather than causing unexpected behavior for callers.

**WASM defensive data length check** — [rippled#6449](https://github.com/XRPLF/rippled/pull/6449) adds a size guard in `EscrowFinish::doApply()` to ensure WASM-produced `sfData` cannot exceed the protocol's maximum allowed length before being written to the ledger entry.

**EscrowFinish assorted fixes** — [rippled#6376](https://github.com/XRPLF/rippled/pull/6376) (+116/-60) improves error comments, hardens `SField` error handling, removes the possibility of negative gas limits, and cleans up memory bounds error handling in the WASM/smart escrow path.

**xrpl-py: SField serialization fix for DynamicMPT and Lending** — [xrpl-py#918](https://github.com/XRPLF/xrpl-py/pull/918) corrects two field code mismatches in the binary codec `definitions.json`: `sfMutableFlags` was assigned field code `nth=54` instead of the correct `nth=53` (colliding with `sfStartDate`), and `sfPreviousPaymentDueDate` was misnamed. Both bugs would cause xrpl-py to serialize these fields with wrong codes, corrupting transactions on the write path. Developers using xrpl-py to interact with DynamicMPT (XLS-94) or Lending Protocol (XLS-66) types should update immediately.

## Plain English Summary

**The network's self-description just got a lot more complete.** When a developer connects to an XRPL node and asks it to describe itself — what kinds of transactions exist, what fields they have, what flags they support — the node can now answer that question fully from its own data. Previously, developers had to hardcode this information in their libraries or maintain separate lookup tables. Starting with this week's merged change, the node delivers transaction formats, ledger entry formats, and flag values directly in its response, meaning client libraries can stay in sync with the ledger's actual protocol without manual updates. This closes an issue that had been open since 2024.

**A serialization bug in xrpl-py could have quietly corrupted transactions.** If you build applications in Python using the xrpl-py library to interact with DynamicMPT (a type of configurable token) or the Lending Protocol, you should update to the latest version. A mismatch in how field codes were assigned meant that certain fields were being assigned the wrong identity number when encoded for the network — like writing the wrong label on a form. This would cause the network to reject or misinterpret transactions. The fix correctly maps two field codes that had been swapped, and also corrects a field that was given an outdated name.

**The XRPL developer documentation has been significantly reorganized.** The tutorials section of xrpl.org has been restructured from the ground up across more than 400 files — content is now grouped by topic rather than listed flat, making it easier to find relevant guides. A long-standing bug where tab selection didn't work on small browser windows has also been resolved. Separately, the llms.txt file that AI tools use to index the XRPL docs has been trimmed from roughly 384,000 characters to about 116,000, making it much more usable for AI-assisted development workflows. Developers building with XRPL should check the updated docs at xrpl.org. Follow [@XRPLF](https://x.com/XRPLF) and [@RippleXDev](https://x.com/RippleXDev) for ongoing updates.

# XRPL Developments Weekly Summary: Mar 2 – Mar 8, 2026

## TL;DR
This week's highlights are spread across infrastructure and protocol work: in rippled, the `server_definitions` RPC was significantly enhanced to include transaction and ledger entry formats and flags (closing a long-standing request), and a major codebase reorganization continued with transactor files split into per-class files and a large ledger-entry view refactor. ## Plain English Summary

**`server_definitions` gets a long-awaited upgrade in rippled**

One of the more impactful changes merged this week (to rippled's `develop` branch — not yet live on mainnet) is an enhancement to the `server_definitions` API call. Previously, this call returned basic information about the XRP Ledger's data types. Now it also includes the complete list of transaction formats, ledger entry formats, and all flag definitions. In practical terms, this means wallets, exchanges, and developer tools can ask a running XRPL node what transaction types exist, what fields they require, and what their flag values mean — without those details being hardcoded into the software. This makes it easier to build tools that automatically support new XRPL features as they're added, rather than requiring a manual update each time. This change closes a feature request that had been open since 2023. It is not yet part of any released version of rippled; it will ship in a future release.

**A crash bug reported for amendment-blocked nodes**

A community contributor this week filed a bug report describing a scenario where XRPL nodes that are "amendment-blocked" (meaning they have not upgraded to support a new network feature) could crash when the network switches to a new ledger state. Specifically, when a node in this state encounters a transaction containing fields it doesn't recognize, it may throw an unhandled error and shut down. This was discovered and reproduced on a related network (Xahau); it has not yet been confirmed on rippled itself. A fix is being developed. If you run a validator or node and you are behind on upgrades, this is worth monitoring. The issue is tracked at [rippled#6492](https://github.com/XRPLF/rippled/issues/6492).

**Clio startup bug fixed; xrpl.js gets community contributions**

Clio — the API server that many XRPL applications use to query ledger data — had a regression where it would fail to start unless a cache file was already present on disk. That bug has been fixed this week. Separately, an external community contributor submitted five new PRs to the JavaScript SDK (xrpl.js) this week, including utilities to convert between currency names and codes, cleaner error messages from the transaction validator, and a new property on the `Wallet` class that tells you which cryptographic algorithm was used to create it. These are under review and not yet merged. For ongoing updates, follow @XRPLF and @RippleXDev on X.
